# Launch & Learn after a reviewed MVP

Use current local tools in the authorized customer project. Read `learn-context`,
`act-context` and the saved IDE dossier as needed. Reuse the confirmed intention,
user, problem, evaluation, habitats, first-user avenues, relevant interviews,
research, MVP scope, parked work and limitations. Do not repeat completed discovery.
The founder must review the actual MVP and `act-review finish` before preparing
exposure. A technical pass alone is not a launch or a user outcome.

## Prepare a small, relevant exposure

`learn-prepare` takes `{expectedVersion: 0}` initially, then the current learning
version for a subsequent reviewed build. Optional style selects one_user,
manual_pilot, small_private_pilot, paid_pilot, targeted_outreach, community_post
or public_release; optional routeIds selects up to three already-saved avenues.
These are preparation choices only. Prefer the smallest relevant exposure, and
define any offer and channel-specific wording with the founder before they send it.
Before feedback, prepare with the current version and options to adjust the draft;
after feedback its historical routes stay attached to that evidence.
`learn-pack` reads its persistent launch
pack. It retains the exact user, strongest existing habitat avenues, observations,
inference, route limitations, an honest invitation, one learning objective, the
real MVP task, and three useful things to observe. `learn-context` is compact;
`learn-dossier` is optional private depth. Do not put that dossier in a coding pack.
If learn-context says current is false, the pack and notes are historical. Resume
the affected current IDE or Act step; do not present old routes or decisions as a
newly confirmed launch. Read-only history remains available for continuity.

Default to one relevant user or a small private pilot. Adapt the draft to the
existing channel and founder's circumstances, including personal use or a paid
pilot only where appropriate. Never invent contact details, research, permissions,
customers, successful outcomes or messages sent. Habitat relevance is an inference;
an old observed discussion does not establish recruitment access now. Check channel
rules/route freshness when needed; ask only about missing or stale information.
Explain why the selected route matches this confirmed user. Do not default to
generic startup launch sites. Present the concise pack and a clear next action.

Prepare messages or follow-ups for the founder to review. Do not send DMs/email,
post, scrape contacts, create accounts or deploy. A prepared message is not sent.
Only the founder's supplied report can record outreach. No autonomous outreach
capability exists in these commands.

## Paste what happened

Invite rough notes once. The founder does not fill out a schema or maintain IDs.
With their authorization, minimize/redact private identifiers before local storage;
use stable `u1`, `u2` and `s1`, `s2` pseudonyms. Never infer a real identity or name.
Do not import secrets, private customer files or unrelated records. The core cannot
redact arbitrary prose automatically; the host must review it. Preserve relevant
source attribution in the retained notes without unnecessary personal details.

The host uses `learn-notes-schema` and `learn-import` with expectedVersion, notes,
synthetic and observations. Each observation contains kind, exact excerpt from
notes, userRef/sessionRef (pseudonym or null), theme, outcome, and signal. IDs and
import digests are generated internally. No API call proves the report is true.
For unknown users/sessions retain unknown; do not invent them to pass a guard.
Notes may first be saved with observations `[]`; use `learn-organize` with the
current version, retained importId and observations to organize them once. Duplicate
imports are ignored. Corrections are new attributed notes, retaining contradictions.

Keep these kinds separate: opinion, reported_behavior, observed_behavior,
commitment, payment, repeated_use, technical_result, outreach_sent, conversation,
no_response, feature_request, unknown. A compliment is not willingness to pay;
conversation is not usage; usage is not payment; payment is not market fit.
Label observed usage only when the notes actually describe a witnessed task.
Repeated use needs an explicit uncoached return, not an intention to return.
Payment needs an actual reported completed payment for a defined offer; promised
payment is commitment. Classifications remain founder/host reports, not telemetry.

Use positive/negative/mixed/unknown outcomes faithfully. Silence has unknown
outcome. Use signals value, friction, low_priority, different_problem,
different_user, intention, or none only when the excerpt supports that inference.
Do not label an opinion, feature request, outreach or technical result as a usage
signal. Theme recurrence counts distinct pseudonymous users, not repeated sentences.
Read the source before classifying it; unknown is preferable to guessing.

## Learn and lead the next decision

`learn-summarize` takes expectedVersion. It preserves evidence types, patterns,
contradictions, commitments, unknowns and KEEP / TEST / PARK. Its conservative
recommendation is a starting judgment. Explain the underlying pain beneath feature
requests; only observed relevant friction can justify a smaller core-workflow test.
Requests stay parked. A dashboard request does not authorize a dashboard.

Follow-up questions concern actual usage: where expectations broke, what happened
after the result, the old workflow, or what prompted a return. Ask one relevant
question, not another pre-build intake or hypothetical purchase survey.

For weak results, be candid and supportive. For no response, distinguish route,
message, timing, trust and urgency with the cheapest next exposure test before
changing the product. For stock tools, discuss workflow usefulness only: no claims
of winning trades, investment performance, prediction or portfolio validation.

Small turns are conversational. Substantial synthesis starts with Executive summary,
2-5 sentences, at most three useful observations, two parked requests and one next
recommendation. Say the extra detail is optional and offer evidence, sessions,
contradictions, feature requests and sources. Use a preferred name sparingly only
when explicitly provided in relevant context. Do not fake positivity or shame.

`learn-decide` takes expectedVersion, choice (approve/challenge/pause/resume) and
the actual founder quote. Show the recommendation before recording approval.
Challenge invites corrected evidence and another synthesis; pause/resume preserves
history. Approval records direction, not permission for unseen code or outreach.

For Act: propose the smallest justified change using current scope and permissions;
obtain approval of that concrete scope before edits. For Define problem/user or
Intention: draft only the affected statement from the evidence, save it through
existing IDE operations, confirm it, reassess relevant Evaluate, and require renewed
Evaluation/Act assent. Preserve valid earlier foundations and evidence. Do not
manufacture research or confirmations to unlock a gate. Add only a minimized,
attributed learning finding to IDE; leave raw user notes in private learning history.
For Evaluate: revisit the material uncertainty rather than rebuild. For exposure:
prepare a smaller route/message/task experiment; send nothing yourself.

The first complete learning decision is the M3 stopping point. No M4, billing,
trial system, backend, CRM, analytics platform, team features or automatic features.
