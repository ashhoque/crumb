# M3 founder trial

Use a disposable copy of an existing synthetic M2 fixture first. Do not repeat IDE
or groundwork in a real project that already has confirmed context and a reviewed
MVP. The six automated scenarios use synthetic people, usage and approvals; their
customer programs and test processes are real.

1. In normal Codex, invoke `$crumb`: "Continue from our reviewed MVP. Prepare the
   smallest useful first-user pilot using the user and habitats we already found.
   Send nothing." If its actual MVP review is still pending, review it first;
   do not invent a completed review.
2. Check that Crumb names the existing user/problem and core journey, explains why
   the selected route fits, separates observed route evidence from inference, and
   keeps channel rules/access uncertainty visible. Open the Launch Pack if useful.
3. For a synthetic workspace only, paste: "Synthetic notes: u1 completed the
   comparison but hesitated at the input format. u2 returned without prompting
   for another comparison. u2 requested automatic discovery." Crumb should organize
   this without asking you for IDs, tags or forms. It must retain the synthetic label.
4. Check the summary: core workflow value, setup friction, automatic discovery
   parked, and one small next test. It must not claim trading performance, paying
   users, product-market fit or that it sent outreach. Inspect evidence on request.
5. Challenge the recommendation once, add a conflicting observation, and verify
   both accounts remain. Paste the same notes twice: they should not double-count.
6. Try "Synthetic notes: I sent one invitation and got no reply." Silence must
   remain ambiguous; Crumb should suggest a small route/message check, not a pivot.
7. Approve the next direction. Confirm it stops before code/outreach. A changed
   problem must use the existing confirmation/Evaluate/Act sequence; a small code
   change still needs review of its concrete scope. Do not authorize M4 in this trial.

For actual pilots, only supply notes you are authorized to share. Minimize or
remove private identifiers before saving them; the host does not automatically
redact arbitrary text. Prefer pseudonyms. No raw customer-file import is required.
You control whether to contact anyone. A technical pass is not customer validation.

Manual acceptance still needs an unscripted Codex conversation: warmth, relevance,
truthful classification, useful channel wording and a clear next decision cannot
be established by structural fixture tests alone. Do not invoke invented test users
as real customer proof. Record any mismatch before authorizing M4.

Developer verification: use the pinned runtime with `node scripts/check.mjs` (or
`cec.ps1 check`). It compiles and runs the complete offline M1-R3/M2/M3 suite.
See M3_REPORT.md and docs/development/M3_SCENARIOS.md for actual recorded results.
