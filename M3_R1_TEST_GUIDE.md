# M3-R1 founder trial

Use a disposable customer project and explicitly label any invented research or
founder dialogue synthetic. Do not use private customer notes. These trials verify
conversation quality; passing automated tests does not replace your judgment.

1. In a Crumb-enabled Codex session, continue an existing synthetic IDE example.
   Try natural replies such as "yup", "sounds good" and "that's right" to the
   current displayed statement. Try "maybe" once: it should clarify one thing,
   not demand an exact Yes. Correct a problem once and check it reconfirms only
   the affected foundations/evaluation. It should lead the next useful question.
2. Review Evaluate and the final build-cycle commitment. Agree naturally. Check
   that the response says the context/handoff is saved and asks for the small
   transition. No product code should have changed.
3. In the build-capable session for the SAME local project, say:
   **Continue the Crumb build.** You should not have to repeat the startup. The host
   verifies the handoff, reads permitted relevant repository files, and prepares
   Startup Master, Red Team, Technical Master, Business Master, Groundwork and
   Build Plan as one pack. Review the concise scope plus optional documents.
4. Approve a small scope and its stated automatic-stage/human-checkpoint policy.
   Check that actual commands run, failed checks do not advance, and the first
   meaningful complete workflow stops with simple instructions to try it.
5. Try the normal workflow, one realistic bad input, and anything confusing.
   Tell Crumb what felt wrong or unnecessary. It must not turn every request into
   an automatically implemented feature or proceed beyond the current authority.

For an existing project, confirm that useful source is KEEP, new core work TEST,
and unrelated work PARK. Compare parked files before/after; parking must preserve.
For a fresh project, the customer stack should fit its workflow and constraints.

ChatGPT transition wording is tested as a capability-aware text adapter. Native
ChatGPT Work transport is NOT implemented here. Only use the "same Project" path
when those actual files are accessible to Work; local Codex folders do not become
ChatGPT uploaded sources automatically. Otherwise expect an honest file-access
limitation, not a request to retype research or a claim that Work was opened.

Record: repeated questions, unclear transitions, unearned praise, unnecessary
details, any missing context, and whether the human stop occurred. Preferred name
use should be occasional and based only on what you explicitly supplied.

Recommended next step: run this one unscripted trial, then report the results.
No later revision/M4 is authorized by this guide.
