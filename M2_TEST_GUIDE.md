# M2 founder trial

M1-R3 remains the foundation. This trial checks the small conversation changes and
Act in the existing Codex host. Use a disposable project and synthetic facts first.
No need to run Crumb's internal JSON tools yourself.

## Conversation

Invoke `$crumb` in the existing Crumb Codex project, explicitly select the disposable
customer folder, and describe either an idea or an existing workflow. Expect one
useful question at a time. Supply a constraint and see whether Crumb remembers it,
acknowledges what it changes, and leads the next useful step without generic praise.
Small replies should feel like a conversation, not a report. Research should have a
short Executive summary and optional sources/competitors/detail.

If you say “Call me Alex,” occasional name use is appropriate; otherwise no name
should be guessed from your project, account or path. Correct the user or problem
once: Crumb should revise the affected statement and reconfirm it, preserving
unaffected context. Try an early “just build”: the remaining IDE gates must still apply.

Confirm the intention, user and problem, review substantive Evaluate, and explicitly
choose **Yes — move to Act**. Viewing research or saying yes to the evaluation alone
must not start scope or implementation.

## Act

Crumb should recap the user, pain and learning question, then propose one complete
workflow and one to three capabilities. It should explain why additional features
are parked. In an existing project, ask it to preserve a useful module and park a
working unrelated feature. The scope should show what stays, what changes, the
first stage and an optional full plan.

After **Approve build**, expect a unique customer build pack containing
STARTUP_MASTER.md, BUILD_PLAN.md, GROUNDWORK.md and stage files. It must not overwrite
an existing customer master. Known setup should be reused. Unknown tooling may need
groundwork and technical-risk checks; a simple known project can have a single MVP stage.

Codex should make actual authorized edits, run the relevant commands, report failures
honestly and give you a way to try the result. It must stop after the stage. A stage
review can authorize one next stage; the final intended stage must stop. **Pause**
keeps the current stage. A material change to IDE must hold the old build rather
than silently reinterpret its approval.

## Delivered fixture examples

The executed rehearsals cover a fresh Python client-readiness workflow, an existing
JavaScript parser extended with comparison while preserving a parked dashboard, and
the stock example through the full Define/Evaluate loop and confirmed IDE to Act.
Each uses invented founder replies. The stock sources are the historical M1-R3
research, not newly verified market facts. No real investment advice is generated.

Passing technical tests is not evidence of customer demand. This trial is also the
place to judge whether Crumb's unscripted replies feel natural; authored automated
rehearsals cannot settle that. Stop before Launch & Learn / M3.
