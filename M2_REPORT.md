material question, investigate when the foundations are ready, or shape scope after

Skipped intention remains open without repeated prompting or an unlocked build.

Short conversational replies render without report headings or an unnecessary

Guidance calls for contextual acknowledgements, specific positive feedback, one

## Act behavior

**Entry and scope.** All five M1-R3 agreements remain mandatory: Intention, User,
Problem, reviewed Evaluate and explicit Act readiness. Material changes suspend
an approved run. Act displays a small user/problem/learning recap, one journey,
one to three capabilities, parked work and the first build stage.

Each capability references the current user/problem basis, an existing insight
considered in Evaluation, and a learning objective. Plans include real input,
useful output, failure behavior and minimum persistence. Existing projects require
inspected files. KEEP preserves useful code; TEST is the Building scope; PARK
preserves other work and cannot be a stage write target.

**Approval and persistent context.** The exact plan hash and current version bind
scope approval. Approval authorizes only the first stage. The build pack is written
after approval into a unique run folder under the selected pack directory:

- `STARTUP_MASTER.md`: confirmed foundation, journey, capability/evidence/learning
  traceability, sources and uncertainties.
- `BUILD_PLAN.md`: scope, KEEP/PARK, stages and the intended stopping point.
- `GROUNDWORK.md`: target stack, inspected files, constraints and persistence choice.
- One `STAGE_n.md` per stage: permitted edits, technical acceptance and review stop.

Existing documents are preserved; differing destination content blocks generation.
Exact interrupted writes can be resumed. The pack is context, not portable execution
permission, and its hashes are checked before handoff.

**Proportionate stages.** A known simple project can use one MVP stage. Unknown
tooling starts with groundwork; M0 risk work is included when needed. The bounded
contract supports 1–8 stages and one final complete MVP stage. It does not impose
Crumb's Node/SQLite stack or a five-milestone template on customer projects.

**Native host execution.** Codex obtains the current stage handoff, reads target
instructions/files, makes minimal authorized edits, runs actual checks, and records
commands, output, exit codes, changed-file hashes, run instructions and gaps.
The core does not execute arbitrary command strings. The existing authorized host
performs that work; no new model SDK, background agent or extra host is introduced.

Completion requires every planned check to execute and pass. Failed work stays
partial and can be repaired within that stage. Completed stages enter
`awaiting_review`; the next handoff is blocked until review authorizes one next
stage. Pause/resume retain the stage. Cancel/finish retain all history. The intended
stopping stage cannot continue, including when the stop was deliberately set at M0.

**History.** SQLite schema 3 adds an append-only `act_revisions` journal beside
existing M1 cycles and v2 IDE records. Old records are not reset, rewritten or
deleted. New approved runs can follow stopped/cancelled runs while retaining their
history. Old M1 draft/handoff operations cannot bypass an existing Act journal.
SQLite backups include this history; customer build-pack files remain separate
target files and need the project's normal file backup/version-control process.
